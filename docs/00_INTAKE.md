# 00_INTAKE.md — 案件ヒアリング正本

## このセクションの目的

本ファイルは、顧客ヒアリング・既存資料・コンサル所感を「生の事実 + 引用 + 仮置きラベル」で集約する **案件入力の正本** です。BIZ-01 以降の仕様書を AI または人間が初稿生成する際の唯一の入力源として参照します。

## 0. 編集ルール

- **書く人**: コンサルタント（または PdM）
- **読む対象**: 後続仕様書を起こす AI、案件参加者
- **AI の編集権限**: 読み取り専用。AI が再構成・要約する場合は別ファイルへ
- **更新の流れ**: 顧客から新事実が出たら、まず本ファイルへ追記。仕様書の修正はその後
- **既存記述は消さない**: 古い前提も取り消し線で残し、いつ何が変わったかを §11 変更履歴で追える形にする
- **発言の引用**: `> 「...」（発言者, 日付）` 形式
- **仮置き表記**: コンサルの推測・補完は末尾に `[Assumed: 根拠 / 確認先]` を付ける
- **開示区分**: front-matter `disclosure: internal-only` を原則とする。顧客開示する場合は別ファイル（`00_INTAKE_customer.md` 等）を作成して共有する
- **サンプル値の扱い**: `<!-- SAMPLE START / END -->` で囲まれた箇所はコミュナレ（架空案件）のサンプル。新規案件適用時は SAMPLE ブロックを実値に置換し、タグ行（`<!-- SAMPLE START ... -->` と `<!-- SAMPLE END -->`）も必ず削除する（詳細は `00_README.md` §5-3 参照）

> 以下の SAMPLE は 00_README §0-1 の**パターン A**（コンテンツ主体サイト + 軽量な管理画面）の受託案件例。マルチテナント SaaS・業務システムの案件は本テンプレートの対象外（00_README §0-1・§2-2）。

<!-- SAMPLE START: フォーマット例 — 実際の内容に置き換えてください -->
### 4-1. サービスコンセプト

> 「今のサイトは表示が遅くて、スマホで見た時に離脱されている感覚がある。更新も制作会社に頼まないとできない」（広報担当 田中, 2026-05-23）

→ コンサル所感: 表示速度の改善と、担当者による更新の内製化が同時に求められている。

### 4-2. ターゲットユーザー

> 「展示会で名刺交換した相手が、後でサイトを見て問い合わせてくれるかどうかが重要」（広報担当 田中, 2026-05-23）

→ コンサル所感: BtoB の検討期間中の再訪問・問い合わせ導線が主要な評価軸。

### 4-3. 差別化ポイント

> 「速いサイトにしたいのは当然として、ブログやお知らせを自分たちですぐ出せるようにしたい」（広報担当 田中, 2026-05-23）

→ コンサル所感: 表示速度（エッジ配信）と内製更新（軽量 CMS）の両立が要件の中核。

### 4-4. 技術方針

> 「Astro + Svelte のテンプレートを社内主軸で進めている。LLM は Claude を主に、用途で他も併用」（PdM 田中, 2026-05-23）

→ コンサル所感: 社内既存スタック（本テンプレート。00_README §0-1 のパターン A）に整合。AI 機能は任意採用（PRD-05）。

### 4-5. ビジネスモデル

> 「初期構築費と、その後の月額保守で見積もってほしい」（経営者 鈴木, 2026-05-23）

→ コンサル所感: 受託制作 + 月額保守の典型パターン（BIZ-03 §1）。サブスク型の課金は本案件に該当しない。

### 4-6. ロール設計

> 「サイトを触るのは基本、広報の田中さん 1 人。将来的にアシスタントが増えるかもしれない」（経営者 鈴木, 2026-05-23）

→ コンサル所感: 単一運営・少数ロールで十分（PRD-01 §1-2 の `admin` / `editor` 2 ロールをそのまま適用。多階層権限は不要）。
<!-- SAMPLE END -->
