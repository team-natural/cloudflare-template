# 02-operations-handbook.md — 運用ハンドブックテンプレート

## このセクションの目的

リリース後の日常運用に **最低限必要な実作業** を 1 冊に統合する：サポート窓口（§1）、インシデント初動（§2）、リリース・ロールバック実作業（§3）、バックアップ・データ保持（§4）。旧 OPS-02〜05 の 4 分冊を統合したもので、各章見出しの「（旧 OPS-0N 相当）」注記を手がかりに、受託案件等で分冊が必要になった場合は章単位で復元できる。

技術選定（インフラ・ツール名）は DEV-01 §1 / §2 を正本とし、本書では原則「基盤」「オブジェクトストレージ」等の一般名で記述する。ロールバックの判断基準は DEV-08 §5、SLA 数値は OPS-01 §3 が正本であり、本書は実作業手順のみを持つ。

## 0-H. ハイブリッド編集ガイド（要点）

- 推奨モード: Hybrid（AI 下書き + Tech Lead / サポート担当 確定）
- 人間確認必須: 実際に守れる受付時間、体制人数で回るエスカレーション、ロールバック手順の実行可能性

---

## 0. 対応時間の原則（全章共通）

- 障害対応・サポート対応は **業務時間内（平日 9:00〜18:00）のベストエフォート** とする。
- 時間外・休日は自動アラート（監視・エラー通知）の記録のみを行い、**対応は翌営業日** とする。24/7 の人的オンコールは置かない。
- 体制は **Tech Lead / PdM / サポート担当** の少数ロール（兼務前提）で構成する。

## 1. サポート窓口・エスカレーション（旧 OPS-02 相当）

### 1-1. 提供範囲

- 対象：操作サポート、アカウントサポート（パスワードリセット等）、決済サポート（課金内容確認・領収書）、生成物サポート（AI 機能採用時）、障害受付
- 範囲外：利用者のコンテンツ作成支援、第三者ツール連携の個別実装相談、会計・税務相談

### 1-2. 受付チャネル

<!-- SAMPLE START: フォーマット例 — 実際の体制・チャネルに合わせて変更してください -->
| チャネル | 受付時間 | 対象 |
| --- | --- | --- |
| メール（support@[yourdomain]） | 24h 受付、平日 9:00〜18:00 に返信 | 全プラン |
| ヘルプセンター（FAQ） | 24h（自己解決） | 全プラン |
| アプリ内チャット / 専用窓口（[上位プラン]） | 平日 9:00〜18:00 | [上位プラン] のみ |
<!-- SAMPLE END -->

プラン別の一次応答時間 SLA は **OPS-01 §3-3 を正本** とし、本書では再掲しない。電話受付は提供しない。

### 1-3. エスカレーション

一次対応（サポート担当）で解決しない問い合わせは以下へエスカレーションする。

| 条件 | エスカレーション先 |
| --- | --- |
| 技術的原因の調査が必要（バグ・障害級疑い） | Tech Lead → 障害級は §2 のインシデント初動へ |
| ロール（admin/editor）変更関連 | admin 権限を持つ Tech Lead / PdM |
| 決済トラブル（重複請求・不正請求疑い） | PdM + Tech Lead |
| データ消失の疑い | Tech Lead（§4 のバックアップから調査） |
| 個人情報インシデント | Tech Lead 主導で DEV-02 §12 のフローへ |
| 法的クレーム・著作権侵害申立 | PdM（必要に応じて弁護士へ相談） |

## 2. インシデント初動（旧 OPS-03 相当）

### 2-1. 重大度定義と解決目安

| Severity | 定義 | 例 | 解決目安 |
| --- | --- | --- | --- |
| **P0（Critical）** | サービス全体停止、データ漏洩、決済重複 | アプリ全停止、個人情報漏洩 | **当日中** |
| **P1（High）** | 主要機能の停止または重大なデータ問題 | 主要機能全停止、決済不可、特定ロール全員ログイン不能 | **1 営業日以内** |
| **P2（Medium）** | 一部機能の停止または特定ユーザーへの影響 | 一部 LLM プロバイダ障害（採用時）、特定の Media ファイル取得不能 | **3 営業日以内** |
| **P3（Low）** | UI 不具合、軽微な性能劣化 | 一部画面の表示崩れ | **次回リリース** |

> 上記は運用目安であり、正式な SLA ではない（SLA は OPS-01 §3）。時間外に検知したものは §0 の原則により翌営業日起算とする。

### 2-2. 障害に含めないもの

<!-- TEMPLATE: 「障害でないもの」を明示し、サポート対応の線引きに使う。実プロジェクトに合わせて調整する -->
<!-- SAMPLE START: フォーマット例 — 実際の内容に置き換えてください -->
| 除外区分 | 対応方針 |
| --- | --- |
| 顧客起因の誤操作・誤設定 | 操作ガイドを案内、必要に応じデータ修正を支援 |
| 契約範囲外の機能実装依頼 | OPS-01 §2 の契約範囲を説明し、要望として記録 |
| 外部サービス起因のみの問題（LLM・決済・DNS 等） | 外部ステータスページを案内し復旧待ち（ベストエフォート） |
| 動作保証外のブラウザ・OS での不具合 | 対応環境一覧を案内。対応環境でも再現する場合は障害扱い |

### 2-3. 初動フロー

```
1) 検知（監視アラート / ユーザー通報）
2) Tech Lead が重大度判定（P0〜P3）・対応チャネル（チャット等）で状況共有開始
3) P0/P1: 復旧最優先で原因究明・暫定対応（ロールバック判断は DEV-08 §5、実作業は §3-3）
   P2: 担当者アサインの上、通常対応
   P3: Issue 化して次回リリースに組み込み
4) 復旧確認 → 顧客通知（§2-4）
5) P0/P1 は簡易ふりかえりを GOV-01 に記録（原因・影響・再発防止策）
```

### 2-4. 顧客通知基準

| Severity | 通知タイミング | チャネル | 対象 |
| --- | --- | --- | --- |
| P0 | 重大度判定後、速やかに（30 分以内目安） | アプリ内バナー + メール | 全ユーザー |
| P1 | 判定後 1 時間以内目安 | アプリ内バナー + 影響ユーザーへメール | 影響ユーザー |
| P2 | 復旧見込み判明時 | アプリ内バナー | 影響ユーザー |
| P3 | 通知不要（次回リリースノートに記載） | — | — |

時間外検知の場合の通知は翌営業日とする（§0）。

通知文面テンプレート（初報。復旧報も同形式で【影響時間】【原因】【対応】を追記）：

```
件名: 【お詫び】サービスの一時的な障害について

現在、以下の障害が発生しております。

【発生時刻】 YYYY/MM/DD HH:MM
【影響範囲】 （例：ログイン・全機能 / 一部機能のみ）
【現状】 原因調査中 / 暫定対応中 / 復旧作業中
【復旧見込み】 （例：現時点では未定 / HH:MM 頃を目標）

進捗は随時アプリ内通知でお知らせいたします。

<サービス名>運営チーム
```

### 2-5. 個人情報インシデント

内部報告・行政報告・本人通知の期限とフローは **DEV-02 §12 を正本** とする。検知した時点で他の作業に優先して同フローを開始する。

## 3. リリース・ロールバック実作業（旧 OPS-04 相当）

デプロイ基盤・環境構成・CI/CD・デプロイゲートは DEV-08 §1〜§6 を参照。デプロイの起動方法は **DEV-08 §3 で確定済み**: 検査（CI）は GitHub Actions（`.github/workflows/ci.yml`）、デプロイ（CD）は Cloudflare Workers Builds の GitHub 連携（`dev` → staging / `main` → production）。本章は自動デプロイと手動 `wrangler deploy` の双方を前提に、人間が行う確認作業とロールバック実作業のみを定義する。

### 3-1. 通常リリース手順

```
1) リリース対象 PR を集約し、CI（`pnpm check` = フォーマット / Lint / 型チェック、全テスト。Turborepo で
   `apps/public`・`apps/admin` それぞれに対して実行される）全 Pass を確認
   （CI は導入済み — `.github/workflows/ci.yml` が `dev` / `main` 宛の PR・push で `pnpm check` → `pnpm db:generate` → `pnpm test` → `pnpm build` を実行する。DEV-08 §3）
2) リリースノート（GitHub Release Draft）を作成
3) main へ PR 経由でマージ → `wrangler deploy` を実行（CI 経由 or 手動、DEV-08 §3 参照）。
   Cloudflare Workers のデプロイはエッジでアトミックに切り替わるため無停止
4) ヘルスチェック（全エンドポイントの定義は DEV-08 §9）
   curl https://{APP_URL}/api/v1/health
   curl https://{APP_URL}/api/v1/health/db
   curl https://{APP_URL}/api/v1/health/kv     # KV 採用済み（DEV-01 §1）
   # /health/queue は不要（Queues 不採用 — DEV-01 §1）
5) スモークテスト（§3-2）
6) デプロイ直後はエラー率・メトリクスを Cloudflare ダッシュボード（Workers Logs / Analytics）
   または `wrangler tail` のライブログで監視
   （ロールバック発動条件は DEV-08 §5 — 本書では再掲しない）
7) 異常なし → リリース完了報告 + GitHub Release を Publish
```

マイグレーションを含むリリースは、事前に staging で dry-run し、無停止可能なこと・前方互換であること（DEV-08 §4、D1 マイグレーションは forward-only）を確認してからマージする。

初回リリース前の事前確認は **DEV-08 §7-3 の検証完了チェックリスト** を使用する（本書には持たない）。

### 3-2. リリース後スモークテスト

<!-- TEMPLATE: 本番反映後に実施する最低限の動作確認。コア機能に応じて「主要フロー」を書き換えること -->

```
[ ] トップページ正常表示（エラー・レイアウト崩れなし）
[ ] ログイン / ログアウト動作
[ ] 主要フロー（登録〜コア機能）1 周動作
[ ] フォーム送信・通知確認（テスト送信で受信を確認）
[ ] HTTPS 有効確認（証明書エラーなし）
```

### 3-3. ロールバック実作業

判断基準は **DEV-08 §5 が正本**。該当したら以下を実行する（迷ったらロールバックを優先）。

```
1) コードのロールバック：
   Cloudflare ダッシュボード（Workers > Deployments）または
   `wrangler deployments list` で前デプロイメントを確認し、`wrangler rollback` で戻す
2) マイグレーションを伴う場合：
   - 前方互換マイグレーション → D1 はそのまま（コードのみ戻す）
   - 破壊的マイグレーション → 戻すのではなく、新規マイグレーションで修正
3) データ修正が必要な場合：
   - メンテナンスモード相当の仕組みはテンプレート未実装（実現方式は KV フラグ +
     各アプリの `src/middleware.ts` での判定で確定。実装は必要になった案件側で行う）
   - データ修正自体は `wrangler d1 execute --command '...'`（または管理画面経由）で実行し、
     修正内容は必ず監査ログに記録する
4) ロールバック実施を §2 のインシデントとして記録（P0/P1 相当なら GOV-01 にふりかえり）
```

### 3-4. 緊急リリース（Hotfix）

```
1) main から hotfix ブランチを作成（hotfix/短い説明）
2) 修正 + 関連テスト・静的解析・フォーマッタを通す
3) PR 作成 → 承認は Tech Lead（兼務可）。P0 対応時は事後レビュー可
4) マージ → デプロイ実行（§3-1 の 3、CI 経由 or 手動）→ §3-1 の 4〜7 を実施
5) 修正を開発ブランチにも反映
```

### 3-5. 計画停止（メンテナンスモード）

停止を伴う作業（大規模マイグレーション等）は、OPS-01 §3-4 の通知条件（7 日前通知・月 1 回まで）を満たした上で実施する。メンテナンスモードの実現方式は KV フラグ + 各アプリの `src/middleware.ts` 判定で確定（§3-3 参照。実装は未着手）。作業完了後に §3-1 の 4〜5 を実施する。

## 4. バックアップ・データ保持（旧 OPS-05 相当）

### 4-1. バックアップ方針

DB は Cloudflare D1（Cloudflare マネージドの SQLite 互換データベース）を使用する。D1 には **Time Travel（ポイントインタイムリカバリ）が常時有効**で、分単位の任意時点へ追加コストなしで復元できる（保持: Workers Paid 30 日 / Free 7 日 — 2026-08 確認）。これを第一の復旧手段とし、保持期間を超える長期保管・オフサイト保管が必要な場合のみ `wrangler d1 export` による日次エクスポートを併用する。

<!-- SAMPLE START: フォーマット例 — 案件のプラン・保管要件に合わせて調整してください -->
| 対象 | 方式 | 頻度 / 保持 |
| --- | --- | --- |
| DB（Cloudflare D1） | Time Travel（常時有効・PITR。復元は `wrangler d1 time-travel restore`）+ 長期保管が必要な場合のみ `wrangler d1 export` 併用 | Time Travel: 30 日（Paid）/ 7 日（Free）。export 併用時: 日次 / 30 日超 |
| オブジェクトストレージ（R2、採用時） | 別バケットへの複製（決済済み資産・ロゴ等の重要ファイルのみ） | 日次 / 30 日 |
| 監査ログ | 削除不可・永続保持（PRD-02 §8）。D1 のバックアップに含めた上で長期保管先を確保 | 永続 |
<!-- SAMPLE END -->

### 4-3. データ保管期限の自動削除バッチ

PRD-02 §8 のデータライフサイクルに準拠し、日次バッチで自動削除する（個人情報保護対応）。バッチの起動方法は Cloudflare Cron Triggers で確定（DEV-01 §2。`wrangler.jsonc` の `triggers.crons` で定義し、対応する Scheduled Worker 内で以下の処理を実行する）。Scheduled Worker 本体はテンプレート未実装 — 保管期限付きデータ（Inquiry 等）を実装する案件側で `triggers.crons` の有効化と合わせて追加する。

<!-- TEMPLATE: プロジェクト固有の関数名・実装（Scheduled Worker 内の処理単位）に置き換える -->
<!-- SAMPLE START: フォーマット例 — 実際の内容に置き換えてください -->
```ts
// 毎日 03:00 JST 実行（Cron Triggers — DEV-01 §2）
purgeExpiredInquiries(); // 受信 1 年経過の Inquiry を物理削除（D1 DELETE。DEV-07 §10）
cleanupOrphanedMedia(); // どのコンテンツからも参照されない Media を削除（D1 DELETE + R2 オブジェクト削除）
rotateLogs(); // 操作ログの保持期間超過分を削除（D1 DELETE）
cleanupTempFiles(); // R2 の一時ファイル削除
```
<!-- SAMPLE END -->

- 期限到達前にユーザーへ段階通知する（解約後 1 年の保管期限に対する事前通知。90 日前メール → 30 日前再通知 + アプリ内バナー → 7 日前最終通知 → 削除実行後に完了通知）
- 自動削除は必ず監査ログに記録する（システム起点のため causer は NULL のまま、event: `data.purged`、発生源は properties で示す — DEV-05 §9-1）
- 解約時のデータ保持・エクスポート条件は OPS-01 §4-2 と整合させる

## 5. リリース後に育てる項目

以下は本書ではあえて定義しない。**運用開始後に必要になった時点で GOV-02 に起票して整備する**。

| 項目 | 起票の目安 |
| --- | --- |
| 運用 KPI の目標値・計測（応答時間 p90、解決率、CSAT 等） | チケット量が体感で追えなくなったら |
| チケット管理ツールの導入・移行 | メール + 手動管理で漏れが出始めたら |
| ヘルプセンター（FAQ）の体系化・自己解決導線 | 同種の問い合わせが繰り返されるようになったら |
| ステータスページ（外部公開の稼働状況） | 障害時の問い合わせ集中が負担になったら |
| インシデント対応訓練・バックアップリストア訓練 | 初回の実インシデント対応後 |
| 定例会議体（運用レビュー等） | 非同期の記録（GOV-01/02）で回らなくなったら |
| 技術的負債の運用ルール（返済割当等。分類は DEV-03 参照） | 負債 Issue が滞留し始めたら |
| 依存ライブラリ更新の定期サイクル運用（方針は DEV-01 §7） | セキュリティ通知への対応が後手に回り始めたら |
| 機能廃止プロセス（告知期間・代替提示） | 最初の機能廃止を検討する時点 |
| ナレッジ管理（社内 Wiki・ふりかえりアーカイブ） | GOV-01 への記録だけでは検索性が足りなくなったら |

## 6. 記入時チェックポイント

- §1 の受付時間・チャネルが実際の体制人数（兼務前提）で守れるか
- OPS-01 §3-3 の一次応答 SLA と §1 の受付時間が矛盾していないか
- Severity 定義（§2-1）と解決目安が現実的か（過剰 / 過小でないか）
- ロールバック手順（§3-3）がリリース前に一度実際に試されているか
- 基盤のバックアップ仕様（§4-1）を確認し「要確認」が残っていないか
- §4-3 の削除バッチが PRD-02 §8・OPS-01 §4-2 と整合しているか
- 技術固有名が DEV-01 参照になっているか（本書に選定を書いていないか）
