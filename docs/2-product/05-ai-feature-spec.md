## 2. AI 機能の分類

採用する AI 機能を以下の 6 分類で整理する。

| 分類 | 説明 | 例 |
| --- | --- | --- |
| **生成（Generation）** | ゼロからコンテンツを作る | 画像生成、コピー生成、コード生成 |
| **要約（Summarization）** | 既存コンテンツを短くする | 会議録要約、長文記事要約 |
| **抽出（Extraction）** | 既存コンテンツから情報を取り出す | キーワード抽出、エンティティ抽出 |
| **分類（Classification）** | コンテンツをカテゴリ分け | スパム判定、トピック分類、感情分析 |
| **対話（Conversational）** | ユーザーとの会話 | チャット Bot、Q&A |
| **検索（Retrieval / RAG）** | 既存データから関連情報を検索 | ナレッジ検索、ドキュメント検索 |

- 新バージョンは staging で 1 週間検証後に本番適用
- バージョン変更は GOV-01 に記録

## 5. プロンプト管理

### 5-1. プロンプトの種類

| 種別 | 説明 | 管理場所 |
| --- | --- | --- |
| System Prompt | LLM の役割・制約を定義 | DB（`prompts` テーブル） |
| User Prompt Template | ユーザー入力を組み込むテンプレート | DB |
| Few-shot Examples | 期待される入出力の例示 | DB |

### 5-2. プロンプトの構造化

すべてのプロンプトは以下の構造で管理：

```json
{
  "prompt_id": "feature_name_v1",
  "version": 1,
  "system": "（システムプロンプト）",
  "user_template": "（ユーザー入力テンプレート。{{variable}} 形式）",
  "few_shot": [{ "input": "...", "expected_output": "..." }],
  "constraints": {
    "max_tokens": 1500,
    "temperature": 0.3
  }
}
```

### 5-3. バージョン管理

- プロンプトは DB の `prompts` テーブルでバージョン管理
- 本番投入前は staging で A/B テスト
- 変更履歴は `prompts` テーブルのバージョン列で管理する（DEV-07 §3-4・§6。専用の履歴テーブルは持たない）

### 5-4. プロンプト変更時のフロー

```
1. 新プロンプト案を staging で動作確認
2. A/B テスト（既存プロンプト vs 新プロンプト）を 1 週間
3. 品質指標（ユーザー満足度・正解率等）で判定
4. 採用決定後、prompts テーブルの version を更新
5. GOV-01 に決定を記録
```

## 7. RAG（Retrieval-Augmented Generation）

検索 Q&A 機能を実装する場合の構成。RAG を使わない場合はこのセクションを削除。

### 7-1. RAG アーキテクチャ

```
ユーザー質問
    ↓
1. クエリのベクトル化（embedding）
    ↓
2. ベクトルデータベース検索（スコープ内のドキュメント）
    ↓
3. 関連ドキュメント Top-K を取得
    ↓
4. LLM に「質問 + 関連ドキュメント」を渡して回答生成
    ↓
ユーザーに回答 + 引用元を返す
```

### 7-2. ベクトルデータベース選択

Vector DB の選定正本は **DEV-01 §2**：**第一候補は Cloudflare Vectorize**。追加インフラなしで D1/Workers と統合できるため、本テンプレートの Cloudflare 前提（DEV-01 §1）に最も整合する。

| 選択肢 | 採用判断 | 補足 |
| --- | --- | --- |
| Cloudflare Vectorize | **第一候補**（DEV-01 §2） | Workers から直接バインディング経由で利用可能。追加インフラ不要 |
| 外部マネージド Vector DB | 例外時のみ | 運用要件で Vectorize が不適な場合に GOV-01 で決定し、DEV-01 に追記 |
| pgvector | 不可 | PostgreSQL 専用拡張。本テンプレの DB は Cloudflare D1（DEV-01 §1）であり PostgreSQL を採用しない |

### 7-3. Embedding モデル

<!-- TEMPLATE: モデル・価格は変化が速いため、プロジェクト適用時に最新を確認して置き換える -->
<!-- SAMPLE START: フォーマット例 — 実際の選定に置き換えてください -->
| プロバイダ | モデル（例） | 採用判断 |
| --- | --- | --- |
| OpenAI | text-embedding-3-small | **推奨**（コスパ良好） |
| Voyage AI | voyage-3-lite | GOV-01 決定後に採用可（標準 3 プロバイダ外のため DEV-01 追記必須） |
| Cohere | embed-multilingual-v3 | 多言語サポート優先時。GOV-01 決定後に採用可（標準 3 プロバイダ外のため DEV-01 追記必須） |
<!-- SAMPLE END -->

> Embedding モデルも統合レイヤー（DEV-01 §2）経由で呼び出す。DEV-01 §2 の標準プロバイダ（Claude / Gemini / ChatGPT）以外の Embedding 専業プロバイダを採用する場合は GOV-01 で決定し、DEV-01 に追記する。

### 7-4. データ更新戦略

- データ作成・編集時にバックグラウンドで embedding 再計算
- データ削除時にベクトルデータベースからも削除
- 全件再 embedding はモデル変更時のみ

## 9. AI 出力の検証・サニタイズ

| 検証項目 | 方針 |
| --- | --- |
| 不適切コンテンツ検出 | モデレーション API または自前 NG ワード辞書（具体ツールの選定は DEV-01 §2 のルールに従う） |
| 個人情報マスキング | 出力に PII（電話番号・メール等）が含まれていないか検査 |
| 構造化出力（JSON / SVG / HTML） | スキーマ検証 + サニタイズ（サニタイズライブラリの選定は DEV-01 §2 のルールに従う） |
| 引用元の明示 | RAG の場合、回答に「関連ドキュメント: ○○」と引用元を必須表示 |
| ハルシネーション対策 | 「該当する情報が見つかりませんでした」と素直に返す指示をシステムプロンプトに含める |

## 10. セキュリティ考慮（DEV-02 §9 と整合）

| 観点 | 方針 |
| --- | --- |
| プロンプトインジェクション | システムプロンプトでロール固定、ユーザー入力サニタイズ |
| 機密情報の漏出 | システムプロンプトに機密情報（Secrets・他利用者の未公開データ等）を含めない、ステートレス化 |
| データ送信の同意 | 利用規約への同意で許諾を取得 |
| LLM プロバイダ規約遵守 | 各プロバイダの利用規約・データ保持ポリシー確認 |
| API キーの管理 | ローカルは `.dev.vars`、本番は Workers Secrets（DEV-01 §1、DEV-08 §1、DEV-10 §1-3）。レート制限の上限を設定 |
